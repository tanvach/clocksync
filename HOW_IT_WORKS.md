# Technical Reference: Signal Encodings & Architecture

This document details the low-level signal generation techniques and station protocol specifications used by `clocksync`. It is designed to provide sufficient detail for a skilled engineer to reimplement the logic on another platform.

The frame encoders live in [`timecode.cpp`](./timecode.cpp), which has no Arduino dependencies and is unit tested on a desktop machine (see [Testing](#testing)).

## Architecture

### Carrier Generation
The ESP32 generates the Low Frequency (LF) carrier using the `LEDC` (LED Control) peripheral.
*   **Peripheral**: `LEDC_TIMER_0`, `LEDC_CHANNEL_0`, low-speed mode (available on every ESP32 variant).
*   **Frequency**: 40 kHz, 60 kHz, 68.5 kHz, or 77.5 kHz, set from the selected station each time the carrier starts. (v1.x always ran at 60 kHz because the per-station frequency was never applied.)
*   **Resolution**: 5-bit duty resolution. The LEDC clock divider has 8 fractional bits, so fewer duty bits leave a finer divider: at 5 bits every carrier lands within ~35 ppm of nominal (60 kHz → 59 998 Hz, 77.5 kHz → 77 500.6 Hz), while 8 bits gave errors up to ~370 ppm. Receivers use narrow crystal filters, so this matters for range.

### Amplitude Modulation (AM)
The system simulates AM by switching the PWM duty cycle of the carrier.
*   **High Power**: duty `16/32` (50 %), the strongest fundamental of a square wave.
*   **Low Power**: duty `2/32` (6.25 %). The fundamental of a pulse train scales with `sin(π·duty)`, so this is ~20 % of full amplitude (about −14 dB).
*   **Note**: This is not true analog AM, but "PWM-based attenuation". It works for near-field magnetic coupling because the receiver's AGC treats the reduced duty cycle as a weaker signal.
*   **Off**: when transmission is disabled or the clock is not set, the pin is switched to a floating input so no current flows through the antenna.

### Precise Timing
Each second is divided into 10 slots of 100 ms; every symbol is a pattern of high/low slots.
1.  **Wall-clock slots**: a one-shot `esp_timer` fires at the next 100 ms boundary of the wall clock. On each firing the callback reads `gettimeofday()`, rounds to the nearest slot, sets the duty for that slot, and re-arms itself for the following boundary. Because the slot is recomputed from the clock every time, an NTP step re-aligns the signal within one slot, with no separate resync logic.
2.  **Frames**: when the slot belongs to a new minute (or a setting changed), the callback builds that minute's 60 symbols with `tc_build_minute()`.
3.  **Isolation**: the callback runs in the esp_timer task, so Wi-Fi, HTTP and serial work in `loop()` cannot delay modulation edges. A mutex keeps configuration changes (station, pin, time zone) from racing with the callback.
4.  **Clock validity**: the carrier only starts once the system time is after 2024-01-01 (set by NTP, the web UI or the `d`/`t` commands). v1.x transmitted 1970 when NTP failed, which some clocks accepted.
5.  **NTP**: SNTP re-syncs hourly. The ESP32 crystal drifts ~20 ppm, so the clock stays within ~70 ms between syncs.

### Time Zones
The ESP32's C library only understands POSIX TZ strings (`CET-1CEST,M3.5.0,M10.5.0/3`). [`tzdata.h`](./tzdata.h) maps all ~420 IANA zone names from `zone.tab` to their POSIX rule. It is generated by [`tools/gen_tzdata.py`](./tools/gen_tzdata.py) from the footer line of each compiled zoneinfo file, so it can be regenerated from any newer tzdata. Two caveats:
*   Greenland (`America/Nuuk`, `America/Scoresbysund`) uses negative transition times (`M3.5.0/-1`) that newlib cannot parse; the generator clamps them to `00:00`, so the switch happens one hour late.
*   Morocco's switch back to UTC+0 during Ramadan cannot be written as a POSIX rule, so those zones stay on UTC+1 all year.

The zone name is stored, not the rule, so a firmware update with newer tzdata picks up rule changes automatically. With no zone chosen, each station uses the zone its real clocks expect (see the table in the README).

## WWVB Implementation Logic: `txtempus` vs. `nisejjy`

This project explicitly follows the logic of the reference implementation **[txtempus]** (by Henner Zeller) for WWVB, deviating from the original **nisejjy** logic.

### The Problem (`nisejjy` legacy)
The original `nisejjy` implementation (and many simple Arduino emulators) often attempted to encode **Local Time** into the WWVB frame.
*   **Issue**: WWVB is defined to broadcast **UTC** (Coordinated Universal Time). The receiver logic (the clock itself) handles the time zone and DST offsets.
*   **Symptom**: Clocks would receive "Local Time" disguised as UTC, then apply *another* offset, resulting in the display being wrong by (GMT Offset + DST).

### The Solution (`txtempus` / `clocksync`)
1.  **UTC Base**: The framing bits (Minute, Hour, Day, Year) are populated using `gmtime()` (UTC).
2.  **DST Flags**: Bits 57 and 58 are derived from the selected time zone (US Pacific by default). Every US zone that observes DST switches on the same UTC day, so any of them produce the same bits.
3.  **Result**: The signal is indistinguishable from the real WWVB station. Your clock behaves exactly as it would with a real signal (correctly applying your local timezone settings).

### DST bits are evaluated per UTC day
NIST defines bit 57 as changing at 00:00 UTC on the day DST begins or ends, and bit 58 as changing 24 hours later. `clocksync` therefore sets:
*   bit 57 = DST in effect at **24:00 UTC of the current UTC day**
*   bit 58 = DST in effect at **00:00 UTC of the current UTC day**

giving `00` (standard), `10` (DST begins today), `11` (DST in effect) and `01` (DST ends today). v1.x compared "now" with "now + 24 h", which announced "DST begins/ends today" up to a day early; a clock syncing in the early morning of the day before a change could switch a day early.

> **Reference**: [github.com/hzeller/txtempus](https://github.com/hzeller/txtempus)

## Data Encoding Schemes

The stations use different methods to encode values (Time, Date) into bits.

### 1. BCD (Binary-Coded Decimal)
Most stations (WWVB, JJY, DCF77, MSF) use BCD. Each decimal digit is transmitted separately as a 4-bit binary sequence.
*   *Example*: Minute `42` is sent as:
    *   Tens place `4` -> `0100`
    *   Ones place `2` -> `0010`
*   This makes it easy for simple logic circuits (like 1970s hardware clocks) to decode directly to a 7-segment display digit.

### 2. Binary
Some fields (like "Year" in BPC or "DOW" in DCF77) use straight binary encoding for the entire value, rather than splitting by digits.

### 3. Quaternary (Base-4)
Used by **BPC** and **BSF**.
*   Instead of sending 0 or 1 per second, these stations send one of **4 symbols** per second.
*   This doubles the data rate (2 bits per second).
*   **Signaling**: The pulse width determines the value.

### 4. Pulse Width Encoding (PWM / Shifts)
Used by **WWVB**, **DCF77**, **MSF**, and **JJY**.
*   This is the physical layer encoding: how a single "bit" (0, 1, or Marker) is physically signaled on the carrier.
*   **Concept**: We drop the carrier power (to "Low") for a specific duration *within* the 1-second window.
*   **Start-Low** (WWVB, DCF77, MSF): The second *starts* with reduced power. The duration of this "Low" state defines the symbol.
*   **End-Low** (JJY): The second starts High and ends with a "Low" pulse. The principle of "duration = value" remains the same.

## Protocol Specifications

The signal is constructed of **10 ticks** (100 ms each) per second.
Legend: `H` = High Power (50 % duty), `L` = Low Power (6.25 % duty).

### 1. WWVB (USA) - 60 kHz
*   **Encoding**: Pulse Width Modulation (Start-Low).
*   **Time**: UTC of the **current** minute; the frame describes the instant its second-0 marker starts.

| Symbol | Duration (Low) | Pattern (10 ticks) | Description |
| :--- | :--- | :--- | :--- |
| **0** | 0.2 s | `LLHHHHHHHH` | Binary Zero |
| **1** | 0.5 s | `LLLLLHHHHH` | Binary One |
| **Marker** | 0.8 s | `LLLLLLLLHH` | Frame/Field Marker |

**Frame Layout** (MSB first):

| Second | Field | Description |
| :--- | :--- | :--- |
| 0, 9, 19, 29, 39, 49, 59 | **Markers** | Second 0 starts the frame |
| 1-3, 5-8 | Minutes | BCD tens (40, 20, 10), ones (8, 4, 2, 1) |
| 12-13, 15-18 | Hours | BCD tens (20, 10), ones |
| 22-23, 25-28, 30-33 | Day of year | BCD hundreds, tens, ones (1-366) |
| 36-38 | DUT1 sign | `101` = positive, `010` = negative (sent as `101`) |
| 40-43 | DUT1 | 0.8, 0.4, 0.2, 0.1 s (sent as 0) |
| 45-48, 50-53 | Year | BCD tens, ones |
| 55 | LYI | Leap year |
| 56 | LSW | Leap second warning (0) |
| 57 | DST | DST at the end of the UTC day |
| 58 | DST | DST at the start of the UTC day |

### 2. DCF77 (Germany) - 77.5 kHz
*   **Encoding**: Start-Low.
*   **Time**: German civil time of the **following** minute. The bits sent during 12:34 describe 12:35, which begins at the next minute mark. (v1.x sent the current minute, so clocks ran one minute slow.)

| Symbol | Duration (Low) | Pattern |
| :--- | :--- | :--- |
| **0** | 0.1 s | `LHHHHHHHHH` |
| **1** | 0.2 s | `LLHHHHHHHH` |
| **Minute mark** | none | `HHHHHHHHHH` (second 59) |

**Frame Layout** (LSB first; BCD ones then tens):

| Second | Field | Description |
| :--- | :--- | :--- |
| 0 | M | Start of minute, always 0 |
| 16 | A1 | Summer time change within the next hour |
| 17 | Z1 | CEST (summer time) |
| 18 | Z2 | CET (standard time) |
| 20 | S | Start of time code, always 1 |
| 21-27 | Minutes | BCD |
| 28 | **Parity** | Even parity over 21-27 |
| 29-34 | Hours | BCD |
| 35 | **Parity** | Even parity over 29-34 |
| 36-41 | Day | BCD |
| 42-44 | DOW | Monday = 1 ... Sunday = 7 (v1.x sent 0 on Sundays) |
| 45-49 | Month | BCD |
| 50-57 | Year | BCD |
| 58 | **Parity** | Even parity over 36-57 |
| 59 | **Mark** | No modulation |

### 3. JJY (Japan) - 40 / 60 kHz
*   **Encoding**: **End-Low**.
*   **Time**: Japan time of the **current** minute.

| Symbol | Description | Pattern (High -> Low) |
| :--- | :--- | :--- |
| **0** | Binary Zero | `HHHHHHHHLL` (0.8 s High, 0.2 s Low) |
| **1** | Binary One | `HHHHHLLLLL` (0.5 s High, 0.5 s Low) |
| **Marker** | Marker | `HHLLLLLLLL` (0.2 s High, 0.8 s Low) |

**Frame Layout** (MSB first; BCD tens then ones):

| Second | Field | Description |
| :--- | :--- | :--- |
| 0 | **Marker** | Start of frame |
| 1-3, 5-8 | Minutes | BCD |
| 9, 19, 29, 39, 49, 59 | **Markers** | Position markers |
| 12-13, 15-18 | Hours | BCD |
| 22-23, 25-28, 30-33 | Day of year | BCD, January 1 = 1 (v1.x was a day behind) |
| 36 | **PA1** | Even parity of hour bits 12-18 |
| 37 | **PA2** | Even parity of minute bits 1-8 |
| 41-44, 45-48 | Year | BCD, last two digits |
| 50-52 | DOW | Sunday = 0 ... Saturday = 6 |
| 53-54 | LS1 / LS2 | Leap second (0) |

### 4. MSF (UK) - 60 kHz
*   **Encoding**: Start-Low. Every second carries two bits, A (100-200 ms) and B (200-300 ms); a 1 means carrier off.
*   **Time**: UK civil time of the **following** minute. (v1.x sent the current minute.)

| Symbol | A | B | Pattern |
| :--- | :--- | :--- | :--- |
| **00** | 0 | 0 | `LHHHHHHHHH` |
| **10** | 1 | 0 | `LLHHHHHHHH` |
| **01** | 0 | 1 | `LHLHHHHHHH` |
| **11** | 1 | 1 | `LLLHHHHHHH` |
| **Minute mark** | | | `LLLLLHHHHH` (second 0) |

**Frame Layout** (MSB first):

| Second | Field | Description |
| :--- | :--- | :--- |
| 0 | **Mark** | 500 ms off |
| 17A-24A | Year | BCD |
| 25A-29A | Month | BCD |
| 30A-35A | Day | BCD |
| 36A-38A | DOW | Sunday = 0 |
| 39A-44A | Hours | BCD |
| 45A-51A | Minutes | BCD |
| 52A-59A | End of minute | Fixed `01111110` |
| 53B | Warning | Summer time changes within 61 minutes |
| 54B | **Parity** | Odd parity over 17A-24A |
| 55B | **Parity** | Odd parity over 25A-35A |
| 56B | **Parity** | Odd parity over 36A-38A |
| 57B | **Parity** | Odd parity over 39A-51A |
| 58B | BST | Summer time in effect |

MSF parity is **odd**: the parity bit makes the number of ones in its field odd. v1.x used even parity, so receivers rejected every frame.

### 5. BPC (China) - 68.5 kHz
*   **Encoding**: Quaternary (4-level pulse width).
*   **Structure**: One frame = 20 seconds, repeated 3 times per minute (at 00-19, 20-39, 40-59).
*   **Status**: Reverse-engineered by the original author; unchanged since v1.x and covered by a regression test against the v1.3 code.
*   **Symbols**: `0`-`3` are 0.1-0.4 s low; the frame marker is low for the whole second.

**Frame Layout (20 s sub-frame)**:

| Offset | Field | Description |
| :--- | :--- | :--- |
| 0 | **Marker** | Sub-frame sync |
| 1 | P1 | Sub-frame index (0, 1, 2) |
| 3-4 | Hours | Hour % 12 (base 4) |
| 5-7 | Minutes | Minute (base 4) |
| 8-9 | DOW | Day of week (base 4) |
| 10 | Hour/Parity | PM flag × 2 + parity of 3-9 |
| 11-13 | Day | Day (base 4) |
| 14-15 | Month | Month (base 4) |
| 16-18 | Year | Year (base 4) |
| 19 | **Parity** | Parity of 11-18 |

### 6. BSF (Taiwan) - 77.5 kHz
*   **Encoding**: Quaternary.
*   **Status**: Reverse-engineered; unchanged since v1.x and covered by a regression test.
*   **Layout**:

| Second | Field | Description |
| :--- | :--- | :--- |
| 41-43 | Minutes | Base 4 |
| 44-46 | Hours | Base 4 (hour × 2, parity in the low bit) |
| 47-49 | Day | Base 4 (day × 2, DOW / 4 in the low bit) |
| 50 | DOW | Day of week % 4 |
| 51-52 | Month | Base 4 |
| 53-56 | Year | Base 4 (year × 2, parity in the low bit) |

## Testing

`make -C test` builds and runs two host-side test programs:

*   **`test_timecode`** checks hand-derived golden frames for JJY, WWVB, DCF77 and MSF; decodes about 3 600 encoded minutes per station across 2026-2028 (plus New Year, leap day and DST-change edges) with decoders written independently from the specs; checks WWVB DST bits around every 2026 US transition, the DCF77 A1 and MSF 53B warning windows, and that BSF/BPC output matches the v1.3 code exactly.
*   **`test_tzdata`** checks that every POSIX rule in `tzdata.h` gives the same UTC offset and DST flag as the host's zoneinfo database, hour by hour, for three years. It skips that comparison when the host's tzdata version differs from the table's.

`python3 tools/device_test.py <host>` runs end-to-end checks against a real device: NTP and clock agreement, the WWVB frame on air decoded against the current UTC minute, API guards and validation, and the carrier frequency for every station as read back from the LEDC registers. On an M5Stack Atom Lite (v2.0.0, core 3.3.5) the readbacks were:

| Station | Nominal | LEDC | Error |
| :--- | :--- | :--- | :--- |
| JJY 40 kHz | 40 000 Hz | 40 000 Hz | 0 ppm |
| JJY 60, WWVB, MSF | 60 000 Hz | 59 998 Hz | −33 ppm |
| BPC | 68 500 Hz | 68 500 Hz | 0 ppm |
| DCF77, BSF | 77 500 Hz | 77 501 Hz | +13 ppm |

v1.x configured every station for 60 kHz, which its 8-bit resolution turned into about 60 015 Hz (+250 ppm).
